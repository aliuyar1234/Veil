# Research: Cryptographic Protection

**Feature**: 010-crypto-protection
**Date**: 2025-12-15

## Research Summary

This document captures research findings and decisions for the cryptographic protection module in Veil.

## Decision 1: Encryption Library

**Question**: Which Rust crate should be used for AES-256-GCM encryption?

**Decision**: Use `aes-gcm` crate

**Rationale**:
- Pure Rust implementation with no C dependencies
- RustCrypto project - widely trusted, audited
- Supports AES-256-GCM as required by spec
- WASM-compatible (critical for browser support)
- Actively maintained with regular security updates
- Constitution requires audited crypto libraries

**Alternatives Considered**:
- `ring`: Fast but has C bindings, complicates WASM
- `openssl`: C dependency, not suitable for WASM
- `sodiumoxide`: libsodium bindings, C dependency

## Decision 2: Hashing Library

**Question**: Which Rust crate should be used for SHA-256/SHA-512 hashing?

**Decision**: Use `sha2` crate from RustCrypto

**Rationale**:
- Part of RustCrypto project (same ecosystem as aes-gcm)
- Pure Rust, WASM-compatible
- Supports both SHA-256 and SHA-512
- Can combine with HMAC for keyed hashing via `hmac` crate

**Alternatives Considered**:
- `ring::digest`: Not pure Rust
- `sha-1` + `sha2`: sha-1 is deprecated for security use

## Decision 3: Random Number Generation

**Question**: How to generate cryptographically secure random bytes?

**Decision**: Use `rand` crate with `rand_core::OsRng`

**Rationale**:
- `OsRng` uses OS entropy source (CSPRNG)
- Works on all platforms including WASM (via Web Crypto API)
- Required for IV generation, salt generation, token creation
- Constitution requires CSPRNG for security

**Alternatives Considered**:
- `getrandom`: Lower-level, rand already provides nice API
- Custom PRNG: Never roll your own crypto

## Decision 4: Pseudonymization Strategy

**Question**: How to generate realistic fake data for pseudonymization?

**Decision**: Use `fake` crate with locale support + deterministic seeding

**Rationale**:
- Supports multiple locales (de_DE, en_US, etc.)
- Generates realistic names, emails, addresses
- Can be seeded for deterministic output
- Pure Rust, no external dependencies
- Supports the required data types: names, emails, addresses

**Alternatives Considered**:
- Custom dictionary: More work, less coverage
- `fakeit`: Less locale support than `fake`

## Decision 5: Token Generation

**Question**: How to generate secure random tokens for tokenization?

**Decision**: UUID v4 with cryptographic random source

**Rationale**:
- Standard format, widely understood
- Sufficient entropy (122 random bits)
- Can use `uuid` crate with `v4` feature
- Alternative: hex-encoded random bytes for more entropy

## Decision 6: Token Vault Interface

**Question**: How to design the token vault storage abstraction?

**Decision**: Trait-based design with in-memory default implementation

**Rationale**:
- `TokenVault` trait allows pluggable backends
- In-memory implementation for testing/simple use cases
- External implementations can use Redis, PostgreSQL, etc.
- Follows constitution principle of simplicity

**Interface Design**:
```rust
pub trait TokenVault: Send + Sync {
    fn store(&self, token: &str, original: &str) -> Result<(), VaultError>;
    fn lookup(&self, token: &str) -> Result<Option<String>, VaultError>;
    fn delete(&self, token: &str) -> Result<bool, VaultError>;
    fn exists(&self, original: &str) -> Result<Option<String>, VaultError>;
}
```

## Decision 7: Output Formats

**Question**: What encoding formats should be supported?

**Decision**: Base64 for encryption output, Hex for hash output (configurable)

**Rationale**:
- Base64: Compact for binary data like ciphertext
- Hex: Standard for hash output, easier to verify
- Both are ASCII-safe for storage/transmission
- Use `base64` and built-in hex formatting

## Decision 8: Key Management

**Question**: How should encryption keys be handled?

**Decision**: Keys provided externally, never stored or generated by this module

**Rationale**:
- Key management is out of scope per spec assumptions
- Keys passed as byte slices or references
- Module validates key length (32 bytes for AES-256)
- No key derivation in this module (could be separate feature)

## Performance Considerations

Based on spec requirements (10,000 encryptions in <1 second):

- AES-GCM with hardware acceleration: ~1GB/s throughput
- Even without AES-NI: ~100MB/s is achievable
- 10,000 values × 100 bytes average = 1MB → well under 1 second
- Hash operations are similarly fast

## Security Considerations

1. **Never log plaintext**: All operations work on byte slices, no automatic Display
2. **Constant-time comparison**: Use `subtle` crate for comparing MACs/tags
3. **Zeroize secrets**: Use `zeroize` crate for key material
4. **Fresh IVs**: Generate new IV for each encryption operation
5. **Salt uniqueness**: Generate unique salt per hash operation (unless deterministic mode)
